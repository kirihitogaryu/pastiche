# Wiki Style Guide

## Purpose

Write wiki pages that are concise, factual, link-rich, and useful to both humans and AI agents.

The wiki is not an essay surface. It is a vocabulary contract.

## Voice

Use compact, factual prose.

Prefer:

```txt
Use `serpent` when a snake-like creature is visibly depicted.
Use `python_(mythology)` only when the source, title, inscription, or iconography identifies the creature as Python.
```

Avoid:

```txt
This tag evokes the serpentine and mythic terror of ancient divine conflict.
```

## Brevity

Write like a Wikipedia contributor who knows that brevity is the soul of wit.

- Keep definitions short.
- Put rules before background.
- Use examples instead of long explanations.
- Remove filler, hedging, and decorative phrasing.
- Avoid "Claudisms", purple prose, and generic AI-style transitions.

## Markdown Structure

Use stable section names. Do not invent clever headings.

Recommended order:

1. `Definition`
2. `Use When`
3. `Do Not Use When`
4. `Common Mistakes`
5. `Related Tags`
6. `AI Tagging Guidance`
7. `Citations`

Rules:

- Use one claim per bullet.
- Put tag slugs in backticks, such as `serpent`.
- Keep relationship lists in frontmatter and explain only important boundaries in prose.
- Keep examples and counterexamples short enough to scan.
- Use Markdown links for external citations.
- Avoid tables unless the structure is genuinely tabular.

## Links

Inline links to other tags are strongly encouraged.

Use links to clarify boundaries:

```txt
Use `serpent` for a visible snake-like animal. Use `python_(mythology)` when the image specifically depicts the mythological Python.
```

Comparison links are especially valuable:

```txt
Use `bow` for the object. Use `drawing_bow` for the action of pulling a bowstring.
```

## Citations

Citations are required when a page makes a non-obvious factual claim.

Always cite:

- art movements
- historical periods
- artist biography
- attribution guidance
- iconographic or mythological interpretation
- technical printmaking claims
- extraordinary claims

Usually do not cite:

- obvious visible objects
- simple usage rules
- app-specific governance rules

## Good Wiki Pages

A good page:

- defines the concept quickly
- explains use and non-use
- names nearby/confusable concepts
- links to better alternatives
- states AI behavior
- gives examples and counterexamples when the boundary is not obvious

## Bad Wiki Pages

A bad page:

- sounds impressive but does not guide tagging
- repeats the label in prose without defining it
- makes unsourced historical claims
- creates subjective vibe rules
- omits confusable tags
- fails to say whether AI can use the tag
